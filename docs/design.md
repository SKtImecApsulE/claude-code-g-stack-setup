## Problem Statement

The user wants a personal assistant that "manages my day and any other task I tell it to do." Concretely: email triage and replies, scheduling and calendar management, files and digital chores — an agent that takes actions, not one that just answers questions. It lives in a chat app (Telegram first) so it can be reached from anywhere and can message proactively (morning briefings, nags, "done ✓" confirmations).

## What Makes This Cool

Every project in this space is "a Telegram bot that reads Gmail." This one inverts the frame: **the trust system is the product, the integrations are plug-ins.**

- **Promotion with receipts.** The agent tracks its own per-task-type record ("I've drafted 14 unsubscribe replies; you approved all 14 unchanged") and proactively pitches for more autonomy with evidence. You promote and demote task types like managing an employee. Nobody has built the agent that *earns* autonomy.
- **One-word undo.** Because every action lands in a ledger with an inverse action recorded, `undo` in chat rolls back the last action(s). Undo is the killer trust feature and falls out of the ledger almost for free.
- **The delegation loop.** What the user actually wants (their words: "any other task I tell it to do", plus proactive "done ✓" messages) is the *feeling of delegating* and getting a checkmark back: assign → progress → done ✓ → trust grows.

## Constraints

- Single user (the builder), personal tool. Optimize for daily use fast, not multi-tenancy or polish.
- Chat-first: Telegram v1 (Bot API is trivial); WhatsApp/voice later.
- Tiered autonomy from day one: auto-execute safe actions; draft-and-confirm risky ones; some actions always escalate.
- Self-hosted always-on service (small VPS or home machine, Docker).
- Google account (Gmail + Google Calendar) is the key integration. **Step 0 of the integration (outside-voice tension 3):** flip the OAuth app from "Testing" to "In production" (unverified is fine for a single user) and verify whether refresh tokens become permanent — this may delete the weekly re-auth constraint entirely (restricted Gmail scopes add nuance; verify, don't assume). The **5-minute token-validity probe stays regardless** (~20 lines; catches revocations too) and the bot must alert the user when credentials die (silent credential death is the "always-on goes deaf" failure). The DM-the-OAuth-URL re-auth flow is built only if weekly expiry survives the production flip; redirect strategy (loopback vs. hosted) decided with the hosting choice.
- Running cost is accepted but bounded (eng review D12): **dumb rules pre-filter continuously (free); LLM triage runs 3x daily** (7am briefing + midday + evening sweeps); owner chat messages are always handled realtime. Budget: **$2/day soft warning DM, $5/day throttle** (agent pauses self-initiated work and says so); both tunable in the task_types DB.
- The alert channel itself can die (Telegram token revoked, process crash, network partition) — and a dead bot can't report its own deafness. Dead-man's switch: the 7am briefing doubles as a heartbeat ("no briefing by 7:05 = check the box"), plus an optional external uptime ping (e.g. healthchecks.io) on the VPS.

## Premises (agreed)

1. Single user, personal tool — optimize for daily use within 2 weeks (stretch: usable by day 2), not other users or polish.
2. Reuse an existing open-source agent runtime (chat gateway + LLM + tool loop); do NOT write that plumbing from scratch.
3. The custom build is the trust layer: action ledger (everything it did, visible), tiered permissions, promote-to-autonomous per task type.
4. Runs as the user's own small always-on service; connecting Google (Gmail + Calendar) is the key setup step.
5. The most dangerous failure is a silent wrong action: every action logged, visible in chat, reversible where possible (archive not delete, draft not send).

Policy guardrails adopted from landscape findings:
- Dumb rules for legible patterns (sender/domain filters); LLM only for judgment calls.
- **Owner-only access:** the gateway rejects all messages not from the owner's Telegram user ID (allowlist checked before anything else). A bot with Gmail/Calendar write authority must not answer strangers.
- No send authority at the `auto` tier; financial email (invoices, payments, wires) always escalates, never autonomous.
- No invisible auto-archive: daily digest of everything archived, with one-tap unarchive.
- **Task-type classification is deterministic, not self-reported:** the tier gate maps tool name + argument rules (e.g. `gmail.archive` + sender-matches-newsletter-list) to a task type. The LLM never declares its own task type — otherwise it could misclassify its way past the gate. Any tool call that matches no rule defaults to `always-escalate`.
- **Prompt-injection defense (eng review 2A, patched per outside-voice tension 1):** email and file contents are untrusted input — anyone can email you. Provenance is tracked at the **session level**, not per-call (per-call provenance is not determinable from inside one LLM context): any agent session whose context contains untrusted content marks ALL its tool calls content-triggered, and content-triggered calls never run at `auto` regardless of the task type's earned tier. This includes the scheduled triage crons — they read email, so they are content-bearing by definition. The agent must cite which message motivated any proposed action. Consequence accepted knowingly: `auto` tier applies mainly to owner-commanded and content-free scheduled actions, so promotions accrue slowly — the trust layer is being built deliberately (it's the point of the project), not because v1 economics demand it.
- **Trust state is data, not config (eng review decision 3A):** a `task_types` table (name, tier, classification-rule ref, streak counters) lives in the same SQLite DB as the ledger; promotions/revokes are single transactions; the owner's 10-task starter list ships as a seed migration; `/policy` in chat inspects it. No YAML tier file — one source of truth.

## Approaches Considered

### Approach A: Bare-bones own service (minimal viable)
~500-line Python service (python-telegram-bot + Claude API tool loop), Gmail/Calendar via MCP, SQLite ledger, tier gate, undo. Effort: S (human: ~1-2 weeks / CC: a weekend). Risk: Low. Pros: every line understood (best pure learning); no framework churn; ships fastest. Cons: every future capability is hand-written; all plumbing bugs are yours. Reuses: MCP servers for Gmail/Calendar.

### Approach B: OpenClaw runtime + custom trust plugin (ideal architecture)
Self-hosted OpenClaw carries channels, sessions, cron, and the skill ecosystem; the custom work is only the trust layer (ledger + tier gate + promotion + undo) as permission middleware. Effort: M (human: ~2-4 weeks / CC: ~2-3 days). Risk: Med (framework dependency). Pros: "any task I tell it" via existing skills; WhatsApp/voice later for free; rides upstream fixes. Cons: framework learning curve; trust layer tracks the plugin API. Reuses: OpenClaw runtime, Gmail/Calendar MCP servers, existing skills.

### Approach C: Claude Code as the runtime (creative)
Thin Telegram bridge spawns Claude Code sessions on the server; PreToolUse hooks are the tier gate; files/shell/browsing work day one. Effort: S-M (CC: ~1-2 days). Risk: Med-High (coding-agent-as-daemon is unconventional; always-on reliability and cost). Pros: maximal raw capability; hooks give the permission gate nearly free. Cons: not purpose-built for chat UX; heavyweight daemon.

## Recommended Approach

**Approach B — OpenClaw runtime + custom trust plugin.** Rationale: premise 2 forbids rebuilding plumbing; the "any other task I tell it to do" ambition needs a real skill ecosystem rather than hand-written tools; and the genuinely novel, fun part — the trust layer — remains 100% custom work. User approved B in session.

### v1 scope (build order)
1. OpenClaw self-hosted (Docker, small VPS or home box), Telegram channel, Claude as the brain.
2. Gmail + Google Calendar via existing MCP servers (test-user OAuth; credential-death alert from day one).
3. **Trust layer plugin (the core build):**
   - Action ledger: append-only SQLite — what, why, task-type, tier, `reversible` flag, how-to-reverse, undo pointer.
   - Tier gate **(eng review decision 1A)**: implemented as OpenClaw's `before_tool_call` hook returning `requireApproval` for `draft-and-confirm` items — OpenClaw owns pausing, Telegram delivery, resume/cancel, and restart survival; we do NOT build a custom queue, inline-keyboard plumbing, or serialized replay. The plugin contributes only the decision: `auto` / `draft-and-confirm` / `always-escalate`, keyed by deterministically classified task type (see guardrails). Hook errors fail closed (escalate).
   - Pending-approval staleness: on approval, preconditions are re-validated (event time still in the future, email thread unchanged since draft); items expire after a TTL (default 24h) with a notification instead of executing stale. `/pending` lists open approvals — `undo` never touches pending items, it operates on executed ledger entries only.
   - ✏️ edit flow: ✏️ prompts "reply with your edits"; a **fresh, stateless agent invocation** over the serialized payload applies them and re-presents ✅/❌ (no session state is retained for the edit path — it's a new LLM call, keeping the "nothing waits on agent memory" property honest). Edits neither count toward nor reset the promotion streak.
   - Promotion state machine, v1 defaults (tunable): 10 unedited approvals of a task type with no intervening ❌ or `revoke` → agent pitches promotion with its record; any ❌ or `revoke` resets the streak; one-tap grant. Demotion: `revoke <task-type>` is the single demotion verb — used both to flag a mistake made at `auto` and to withdraw trust preemptively — dropping the task type back to `draft-and-confirm` and resetting its streak.
   - Undo executor: strictly LIFO over executed ledger entries (`undo` = last action, `undo 3` = last three); ledger entry → inverse action (unarchive, delete calendar hold, discard draft). **Preconditions before every inverse (outside-voice tension 4):** re-validate the target's current state first (message still archived? hold still unaccepted?) — reversibility is time-dependent, the flag written at action time can go stale; on mismatch, report "the world changed, here's what I found" instead of acting. Every inverse execution appends its own ledger entry (the undo path is itself ledgered — "100% of actions in ledger" includes undos, and undo-of-undo is just the next LIFO entry). Actions marked `reversible: false` (e.g. a sent email) make `undo` reply with what it can't reverse and why; a multi-step `undo N` **halts** at the first irreversible entry, failed precondition, or runtime failure (entry marked `undo_failed`, error reported in chat) rather than skipping past it.
4. Proactive loop: 7am briefing cron (calendar + inbox summary), archive digest with one-tap unarchive, "done ✓" confirmations.
5. Later (10x roadmap): files & digital chores, WhatsApp, voice, memory/RAG, weekly performance-review message.

## Success Criteria

- By day 2 (stretch): it sends the 7am briefing and the user approves one drafted email reply from their phone.
- Within 2 weeks: daily use — triage digest reviewed daily, the promotion pipeline exercised end-to-end (a real high-volume task type or a synthetic drill), zero silent actions (100% of actions in ledger and visible in chat). Real-world promotions are expected to accrue slowly under the session-provenance rule — accepted (tension 1); the streak threshold gets recalibrated from observed approval volume after dogfooding.
- Trust test: `undo` works on every reversible action type in the ledger.
- Reliability: bot messages the user within ~10 minutes of its Google credentials expiring (5-minute probe interval plus delivery), with the re-auth URL in the same message.

## Distribution Plan

Personal self-hosted service: Docker Compose on the user's VPS/home machine; config + secrets via `.env`. The ledger SQLite lives on a named Docker volume (it's the trust anchor — it must survive container recreation), with a nightly `sqlite3 .backup` copy to a second path as the one-line backup story. Repo holds the compose file, the trust-layer plugin, and setup docs. No public distribution in v1 (single user). CI: GitHub Actions building the plugin image on merge is a later nice-to-have; manual `docker compose up -d` is fine for v1.
